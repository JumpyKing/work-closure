# review — 冻结与审查

## S/M：diff 审查

- 基准：只把工作单白名单内、自检通过的文件提交到任务分支，以该 commit SHA 为基准；负载不在 git 中或未获提交授权时，以改后文件的逐文件 SHA256 清单为基准，并留存起点备份。起点（base commit 或改动前备份）与基准一起写入检查点。
- 输入：起点到基准的 diff、工作单与验收标准。diff 必须如实反映文件内容，不得改写内容行（非 git 负载可用 `git diff --no-index` 生成）；diff 随审查提示传入，过长时写入审查 workspace 内的文件，提示里给出路径。审查者可按需只读相关文件核对上下文，不整库通读。
- workspace：审查 workspace 为基准的干净检出，不含被 .gitignore 忽略的本地凭据与配置：git 负载在账本目录下用 `git worktree add --detach` 检出基准 commit，非 git 负载为白名单文件的副本目录。diff 文件放在检出内；报告保存在检出之外的账本中。
- 路线：审查 A 为 Sonnet；M 级另加审查 B 为 Grok，两路各自独立，互相看不到对方意见。Claude Code 宿主内 Sonnet 可用 Agent 工具指定模型；其他宿主经 `scripts/run_cli.py` 调本机 `claude` CLI。Grok 经 `scripts/run_cli.py` 调 cursor-agent。argv 见 `references/routes.md`。经包装器的一路仍须 summary `status=ok`、`exit_code=0`、`model_match=true`。Agent 工具路线没有工具级只读保证，主对话在审查前后各核对一次审查检出未变（git 检出看 HEAD 等于基准且 `git status` 除放入的 diff 文件外无改动，副本目录看文件 SHA256 清单），变了即 `review_incomplete`。
- 报告：明确 APPROVE/REVISE，并列出意见或明确写出未发现问题。主对话把每一路报告原样存入账本，记录报告路径、报告 SHA256 与所审基准；报告与基准的对应关系由主对话按发出的 diff 记录，不要求审查者抄写哈希。
- 修复后：重新提交（或重算文件 SHA256 清单）得到新基准，只把上次已审基准到新基准的增量 diff 交给本级全部审查路线复审；增量复审同样计一轮。定级升级时，新增的审查路线审起点到当前基准的全量 diff；升到 L 级按 L 重新冻结并两路全量审查。
- 交付前核对：实际交付的 commit SHA（或交付文件的逐文件 SHA256）必须等于最后一轮全部 APPROVE 所对应的基准，不符即 `review_incomplete`。

## L：冻结清单

- 逐文件 SHA256：对负载每个文件计算 SHA256，与相对路径一起记录。
- 集合摘要：每个文件一行，格式为 `相对路径\tSHA256`（制表符分隔，行尾换行），按路径排序后把全部行拼接成一段文本，对该文本再取一次 SHA256。
- 冻结清单与集合摘要写入检查点与审查记录，两路审查与安装比对绑定同一集合摘要。
- 冻结后负载任意一个字节变化（含空白与换行）即视为新负载：重新计算清单并重新双审。

## L：两路审查

- 审查 A 使用 `claude-sonnet-5-5`，经 `scripts/run_cli.py` 调本机 `claude` CLI；审查 B 使用 `grok-4.7-high`，经 `scripts/run_cli.py` 调 cursor-agent；保留两份原始事件流与 summary。
- workspace 区分：规划 workspace 是本次真实任务目录；两路审查 workspace 是各自独立的冻结副本目录，任一路的副本不包含另一路的意见与结论。
- 真实审查证据门（逐路独立判定，以下每一项 Sonnet 与 Grok 各自满足，两路不得共用任何一项证据）：
  - summary 门：每一路的 summary 都必须自己的 `status=ok`、`exit_code=0`、`model_match=true`。
  - 报告门：每一路主对话分别实际读取该路自己生成的 `response.md` 与 `plan.md`，从两者中至少确认一份为该路的完整审查报告（非空、准确绑定本轮 `artifact_sha256`、明确 APPROVE/REVISE，并列出审查意见或明确未发现问题；单纯非空前言、普通实施计划或模型自述不算）。实际 Cursor `plan` 模式可能把完整审查放入 `createPlanToolCall` 对应的 `plan.md`，而 `response.md` 只有前言。
  - 每一路各记：该路 summary 路径、完整报告确切路径、报告 SHA256、`artifact_sha256`、审查结论与意见处理。两路不能共用一份报告，也不能用一路的报告替代另一路。
  - 若同一路的 `response.md` 与 `plan.md` 是两份完整报告但结论冲突，按 REVISE 记录并按意见处理流程闭合，禁止只保留 APPROVE 一份。
  - 任一路 summary 不符、无完整报告，或报告与该路 summary 证据不符，即置 `review_incomplete`，不得当作双审完成，不得安装或标记完成。summary 证据门不因存在 `plan.md` 而放宽；调用成功也不等于审查通过。
- 派发前主对话对每个隔离副本逐文件重算哈希与集合摘要，与冻结清单比对；审查报告保存到副本之外，不写进被审副本；安装或交付前再次重算产物哈希与集合摘要，与报告绑定的 `artifact_sha256` 比对，不符即置 `review_incomplete`。
- 审查报告绑定本轮准确的 `artifact_sha256`；调用成功不等于意见处理完成：阻断问题必须修复并复验，实质问题不采纳须逐条给出有证据的理由，可选与无效意见记录取舍。
- 修订负载任意一个字节后旧双审失效：重新冻结，两路重新审查。

## 审查轮次预算

- 同一工作单在同一验收范围内审查最多三轮，S/M 的增量复审也计一轮。范围内修订、重新冻结、出现新问题、换模型、换对话或定级升级均不清零轮次；轮次写入检查点。
- 第三轮审查结束仍有未闭合的阻断或实质问题时，不启动第四轮，状态置 `stopped_root_cause`：先做根因分析，缩小或重整方案；只有确实需要新的用户授权时才询问用户，不机械增加审批步骤。
- 该审查轮次预算与止损条款的"连续失败三次止损"分开记录，互不替代、互不清零。

## 判定分级

| 级别 | 处理 |
| --- | --- |
| 阻断 | 必须修复并复验后才能继续 |
| 实质 | 应修复；不修复须在检查点记录理由 |
| 可选 | 主对话裁量，记录取舍 |
| 无效 | 不成立的意见，记录驳回理由即可 |

审查与规划均为只读：审查者不修改负载，不具有业务写权限。
